# The visual publisher

The visual publisher is given a page, as datom, and publishes it as made, publicly.

It publishes whatever it is given, at once, every time. What it finds wrong in a page it says after publishing, to the flow that gave it the page; a page given again is published again.

```ethos
Types
[ PicturePath.String
  ModuleType.[ Spirit Intent Vision Knowledge Notion Compensation Inquiry Role Raw ]
  Topic.String
  Version.Integer
  Module.{ ModuleType Topic Version }
  Words.Integer
  UnitKind.String
  FencedSource.String
  Code.{ UnitKind FencedSource }
  Change.[ Added.PicturePath
           Removed.PicturePath
           Replaced.{ PicturePath PicturePath }
           Standing.PicturePath ]
  Unit.{ Change Words Option<Code> }
  SectionBody.[ Archive
                Destroy
                ReplaceModule.Vector<Unit>
                Pictures.Vector<Unit> ]
  Section.{ Module SectionBody }
  VisualPage.{ PresentationName.String
               Signature.String
               Vector<Section> } ]
```

A section body is a bare picture vector for an ordinary section, `Archive` or `Destroy` for a mark-only section, or `ReplaceModule.[ Unit ... ]` for a whole-module replacement. The `Pictures` case in the type above is written as the bare vector. Archive and Destroy each show their own mark with the module heading and have no body. A replacement shows its heading and Replacement mark, then its nonempty picture vector. These forms take no old module source. A removed **picture unit** still uses `Removed.PicturePath`.

A pictured unit with code uses `Some.{ UnitKind «fenced source» }`. The source holds one or more complete Markdown code fences; only whitespace may separate them. The language label, when present, comes from the fence. The publisher displays only the exact code inside the fence and preserves indentation, blank lines, and code characters. The renderer refuses bare code, incomplete fences, and text outside a fence. On narrow screens, longer code lines scroll inside their own block.

{ «WhereAVectorIsRead.1»
  «Created by Fable. Drawn by Sonnet.»
  [ { { Vision example 0 }
      [ { Added.«pictures/1.svg» 19 None }
        { Replaced.{ «pictures/2-out.svg» «pictures/2.svg» } 24 Some.{ ethos «```ethos
Example.String
```» } } ] }
    { { Intent old-method 0 } Archive }
    { { Vision obsolete 0 } Destroy }
    { { Vision sema 0 } ReplaceModule.[ { Added.«pictures/3.svg» 8 None } ] } ] }
````

The page opens with the Presentation name, a PascalCase expression and its revision, and the signature naming the creating and drawing models from the manifest. Each section is headed by its complete module struct. Its drawings keep their order. Added pictures carry a green margin, removed pictures a red margin; a replaced picture unit shows the outgoing picture beside the incoming one. A standing picture has no margin. Word counts are manifest metadata. The page shows the marks, pictures, and code bodies, with their headings and signature.

## Build and publish a VisualPage

For a `page.datom` in the VisualPage form above, build a bundle with the VisualPage renderer. Give it the manifest path and a new directory in the harness scratchpad:

```sh
python3 -I "$HOME/.local/state/curriculum-context/mind-belief/tools/visual-page.py" "$page" "$scratch/page"
```

Use native Artifact to publish `$scratch/page/index.html`, with its path as `file_path` and `$scratch/page` as `root`. `assets.json` gives the relative-to-absolute file map if the tool asks for `files`. For an in-place update, supply the existing page address. Send the published address and its actual sharing state; report findings afterward.

A page given again replaces the one published under the same title.

It gives the sender the page's public address and reports what it finds wrong after publishing.
