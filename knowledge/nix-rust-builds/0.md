The working instance is github.com/LiGoldragon/rust-nix-example, built on github.com/LiGoldragon/build-base. Read it whole before changing a build; when this module and the example disagree, the example is fixed or this module is, in the same change.

## The unit of a build is the crate

Every crate, registry, git and workspace member alike, is its own derivation: crate2nix generates `Cargo.nix` from `Cargo.lock`, nixpkgs `buildRustCrate` builds each crate, and `Cargo.nix` is committed, so evaluation imports no derivation. An edit rebuilds the edited crate and the crates that depend on it, and nothing else.

```nix
{
  inputs.base.url = "github:LiGoldragon/build-base";   # nixpkgs, toolchain, crate overrides: one pin for all
  outputs = { self, base }: base.lib.workspaceOutputs { cargoNix = ./Cargo.nix; };
}
```

```sh
# after any edit to Cargo.toml or Cargo.lock, regenerate and commit Cargo.nix
nix run github:LiGoldragon/build-base#crate2nix -- generate
```

## One base, so a crate has one hash everywhere

Every active repository takes nixpkgs, the Rust toolchain and the crate overrides from build-base. A crate at one version and one feature set then has one store path in every repository, built once on the remote builder and served to all. A native input a crate needs goes in build-base's overrides. A repository's flake, or a consumer of one, takes `pkgs` from `base.lib.contexts.<system>.pkgs` and overrides none of the base's inputs, so store paths stay shared.

Build-base holds one version set, `crate-versions.json`, for every crate a repository takes from another repository: a registry crate by name and version, a git crate by name, version and one locked commit. A workspace member is in neither set. The `crate-versions` check in every `checks.default` refuses a lock that departs from the set, naming each crate with its lock's version and revision and the set's. Beside it, `crate-features.json` holds one feature set per crate name and version: the union of the features the active repositories resolve, applied by build-base's crate builder. The `crate-features` check refuses a repository that resolves a feature outside the set or lacks a dependency the set pulls; that repository then carries the edge itself, its dependency taking the feature in its manifest, lock and `Cargo.nix`. Every such crate is in both sets.

A feature is an input: a crate built with and without a feature is two derivations, each built once. A feature that differs by consumer becomes a crate wherever a crate can carry it: transport left signal as `signal-transport`. Where it cannot, and datom deriving on the signal types is the one such case, the crate holds named sets in place of its union, each a deliberate entry naming the vision line that places the feature per consumer (for datom, vision:ethos:0, "The datom traits are compiled in only where text is spoken"):

```json
{ "sets": [ { "name": "plain", "features": […], "attaches": […], "vision": "vision:ethos:0, …" },
            { "name": "datom", … } ] }
```

Every crate with named sets lists the same names in the same order. A build, a member's, a test build, or one composed through `buildRustCrateForPkgsFor { packageId; features; runTests; }`, takes the first name whose sets hold what it resolves, and every crate in it is built under that name, so no build links two builds of one crate. The generator keeps the named sets as written and writes their `attaches`. It refuses, writing nothing, where no one name holds a member's resolutions, or where a crate's union passes a per-consumer feature on, which makes that crate take named sets too. The `crate-features` check refuses the same in a repository, and a `Cargo.nix` lacking an optional dependency that one of its member's sets attaches.

Build-base hands a crate `default` exactly where its features table declares it and every feature and optional dependency it implies is on, so a crate with an empty `default`, reached with and without default features, is one build (`crate-default-features.nix`).

A version or revision bump happens once, in build-base: the sets are regenerated and every active repository follows in the same change.

```sh
# regenerate the sets from the active repositories; the version set refuses, writing nothing,
# where two locks disagree within one semver line or hold a git crate version at two revisions
nix run github:LiGoldragon/build-base#crate-version-set -- <Cargo.lock ...>
nix run github:LiGoldragon/build-base#crate-feature-set -- <Cargo.nix ...>   # also lists the edges a repository must carry
```

## A Cargo.nix is proved current

`checks.cargo-nix`, in every `checks.default`, proves the committed `Cargo.nix` is what the base's crate2nix generates: the lock's packages against `Cargo.nix`, then an offline regeneration compared byte for byte. `Cargo.nix` sits at the workspace root, generated with no flags, with `crate-hashes.json` committed beside it. A `Cargo.nix` kept apart from its workspace is proved by `cargoNixCheck { source; cargoNix; crateHashes; }`, `source` being the workspace holding `Cargo.toml` and `Cargo.lock`. A repository's own checks join `checks.default` through `extraChecks`, so a green default is the whole gate:

```nix
outputs = { self, base }: base.lib.workspaceOutputs {
  cargoNix = ./Cargo.nix;
  extraChecks = { pkgs, workspace, ... }: { fmt = …; doc = …; };   # names apart from members, cargo-nix and default
};
```

```nix
# a second, separate Cargo.nix joins checks.default the same way
extraChecks = { cargoNixCheck, ... }: {
  dependency-cargo-nix = cargoNixCheck {
    source = ./dependency;
    cargoNix = ./nix/dependency/Cargo.nix;
    crateHashes = ./nix/dependency/crate-hashes.json;
  };
};
```

## A check runs; it does not compile

A crate's tests compile once, with the crate, into test binaries; the crate's one check runs them and compiles nothing. A failing test fails it, and the default check is all of them. A test is named in its code and proved by its crate's check.

A crate builds from its own directory, the one holding its Cargo.toml, without the files its build never reads: `tests/`, `benches/`, `examples/`, Markdown, `Cargo.lock`, `Cargo.nix`, `crate-hashes.json` and the flake files (build-base's `crate-source.nix`). A git crate's directory is cut from its checkout where its Cargo.toml names the package. The test build alone reads the whole directory, so an edit to a test rebuilds the test build alone, and two commits that differ only in those files, or in another crate, are one source path and one build; a member and the same commit taken as a git dependency are one source path. A crate reads only files inside its directory: `include_str!("../ethos/…")` from `src/lib.rs` reads its own.

## A member's library is built once

A crate's version moves only when its own content changes: each workspace member carries its version in its own manifest, and the workspace sets none, since a version every member inherits makes one member's release a new derivation of every member and everything depending on them.

A member's library is built apart from its binaries and tests and carries no binary, so it is one derivation with its git copy in another repository, and every dependent, the member's binaries and its test targets link it. The binaries, `rust_<crate>-<version>-bin`, are compiled alone against that library, reading its build-script output, and are `packages.<member>`. The test build compiles only the library's and each binary's unit tests (`--test`) and the test targets, and runs the binaries' build through `CARGO_BIN_EXE_<name>`. Where dev-dependencies turn on a feature or an optional dependency, the test build compiles its own library and binaries, as cargo builds two. A member reached through `buildRustCrateForPkgsFor` or `workspaceMembers.<member>.build` is its library alone; a flake composes a member's binaries under a feature set with `binaries`:

```nix
composed = base.lib.workspace.${system} { cargoNix = ./Cargo.nix; };
cli = composed.binaries "capsule-nexus-translator" [ "default" "text" ];
```

## The test build is the lint gate

Clippy-driver compiles a crate's test build over every target (library, binaries, unit tests, `tests/`), the library and binaries checked with `--emit=metadata` as `cargo clippy` checks them, with the member's `[lints]`, or the workspace's where it takes them, applied uncapped and `lintFlags` after them. That one compilation lints and makes the test binaries; a refused lint fails the crate's check. A member is linted under its check's feature set, so a feature-gated line is linted by giving its check that set through `memberChecks`.

```nix
base.lib.workspaceOutputs {
  cargoNix = ./Cargo.nix;
  lintFlags = [ "-D" "warnings" ];   # the default
  memberChecks = { check, ... }: { member = check "member" [ "default" "json" ]; };
}
```

`nix flake check` saying "running 0 flake checks" means nothing was left to build; the gate's green is put on record by building `checks.default`.

## Where a build runs

A gate is evaluated and built on the remote builder: nix-fast-build `--remote` runs nix-eval-jobs there, builds each check there over ssh, and copies nothing back under `--no-download`. The local machine compiles nothing, cargo included. The host's own declaration names the remote builder.

```sh
nix run github:Mic92/nix-fast-build -- --remote <builder> \
  --no-nom --no-download --eval-workers 1 \
  --flake 'git+file://<clone>?rev=<commit>#checks.x86_64-linux'
```

The gate builds `checks.<system>` whole, so a failing check is named by its own attribute. Its exit is the result, waited on as an event: the command runs in the foreground, or in the background where its exit wakes the flow that started it. A failure ends the output with the failed attributes, each one's log above it:

```text
ERROR:nix_fast_build:BUILD: 10 successes, 2 failures
ERROR:nix_fast_build:Failed attributes: …#checks.x86_64-linux.example-number …#checks.x86_64-linux.default
```

A gate runs against the committed revision, `git+file://<clone>?rev=<commit>` or the remote URL, since a check that stamps `self.rev` gives another result on a copied tree. A `git+file` revision is copied to the builder as its source store path; a remote URL is fetched by the builder itself.

A build whose result the local machine keeps, such as a package it installs, is a plain `nix build`: the host declares the builder as an ssh-ng remote builder with no local jobs, so every derivation builds there and the result is copied back.

```sh
# /etc/nix/machines: ssh-ng://nix-ssh@<builder> x86_64-linux … ; max-jobs = 0
nix build 'git+file://<clone>?rev=<commit>#<package>'
```

## A pin names a published commit

A git dependency is pinned to a commit its remote has, and a published history stays as published; a build from the repository's remote URL proves it. A flake used as a test fixture is a locked input by its bare URL, its rev asserted at evaluation.

A git dependency under `[patch]` that points at a workspace crate resolves to that path crate in `Cargo.nix`.
