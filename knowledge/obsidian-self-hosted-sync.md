Witnessed 2026-10-29 by fetching each URL. All four are third-party.

**Self-hosted LiveSync** (vrtmrz, MIT). Backends: a CouchDB-compatible server, S3-compatible object storage, and peer-to-peer WebRTC, which still needs a signalling relay for peer discovery. The README says it is available on all Obsidian-compatible platforms and that 1.0 requires Obsidian 1.7.2 or later. The README's status-bar legend mentions "Chunks and Metadata"; its server storage format is not described there. Release 1.0.42 is marked Latest, dated 27 October 2026; its release notes do not mention a headless CLI (the 1.0.36 notes mention "Headless command-line start-up"). The repository holds `src/apps/cli`, whose README describes `livesync-cli`: `daemon` (the default command) runs a mirror scan, then syncs CouchDB and the local vault directory in both directions continuously (CouchDB `_changes` feed or `--interval N` polling; a file watcher pushes local creates, edits and deletes); `sync` runs one replication cycle; `mirror`, `ls`, `cat`, `put`, `push`, `pull` also exist; a Docker image `ghcr.io/vrtmrz/livesync-cli` is named. https://github.com/vrtmrz/obsidian-livesync/blob/main/src/apps/cli/README.md https://github.com/vrtmrz/obsidian-livesync and https://github.com/vrtmrz/obsidian-livesync/releases

**Remotely Save** ("Source Available", license not named on the README page). Free backends: S3-compatible, Dropbox, OneDrive personal (App Folder), WebDAV, Webdis (mostly experimental); PRO adds more. Free conflict handling: it detects conflicts and the user chooses to keep the newer or the larger file; PRO "Smart Conflict" merges small Markdown files. Mobile is supported; the README warns of performance issues on files of 50 MB or more. https://github.com/remotely-save/remotely-save

**Obsidian Git** (Vinzent03, MIT). The README calls Git on mobile "very unstable!", built on isomorphic-git, with no SSH authentication, no rebase, limited repository size, no submodules, and possible crashes or endless runs on clone or pull. https://github.com/Vinzent03/obsidian-git

**Syncthing on Android.** The official Syncthing Android app was retired by its author in the announcement of 2024-10-20; the last release was planned with the December 2024 Syncthing version. A second report gives 2024-12-03 as the archive date; not witnessed here. https://forum.syncthing.net/t/discontinuing-syncthing-android/23002 The fork Syncthing-Fork on F-Droid lists 2.1.7.0, added 2026-10-25, as suggested. https://f-droid.org/en/packages/com.github.catfriend1.syncthingfork

Syncthing-Fork 2.1.7.0 is released at commit `f8819078e7dec1e8a954eec839febd9f7385294e`. It runs a sticky foreground service under configured run conditions and uses a persistent notification; its project documentation requires exemption from Android Doze and warns that manufacturer task killers may need a further exception. `Start automatically on boot` (`always_run_in_background`) defaults to false, so the boot receiver does not restart the service until that setting is enabled. Run-condition defaults are Wi-Fi on, metered Wi-Fi off, mobile data off, roaming off, respect Android battery saver on, respect master sync off, flight mode off and scheduled running off. These are source witnesses, not a phone-runtime witness; screen-off, reboot, vendor battery management, mobile-data operation and background transfer have not been run on the living's phone. Syncthing enables relaying by default and uses a relay when a direct connection cannot be made, while periodically retrying a direct connection. The public relay retransmits end-to-end encrypted traffic; it is a server between the peers and can observe their device identifiers, addresses and traffic amount, but not the file plaintext. Default listen addresses include TCP, QUIC and the dynamic public relay pool; a peer address of `dynamic` uses discovery. An away-from-home route therefore also requires both peers running and online, the phone's current network allowed by its run conditions, relay and discovery settings retained, and outbound relay reach. https://docs.syncthing.net/v2.1.0/users/relaying.html https://docs.syncthing.net/v2.1.0/users/config.html

An isolated execution on ouranos used two temporary Syncthing 2.1.3 desktop peers connected only over loopback. It synchronized a whole vault in both directions, including an attachment, hidden `.obsidian` plugin/settings/snippet files, a same-id Review Comments reply and a linked answer note. Endpoint-local `.stignore` files containing `.obsidian/workspace.json` and `.obsidian/workspace-mobile.json` kept deliberately different workspace files local; Syncthing documents and the execution confirmed that `.stignore` itself is not synchronized, so the patterns must be installed at every endpoint. A change made while one peer was stopped arrived after both ran together again, and a deletion propagated. Concurrent edits produced a winner and a `sync-conflict` copy on both peers when `maxConflicts` was explicitly 10; ordinary configuration defaults this setting to 10 and 0 disables conflict copies. A typed deployment must retain a positive value if conflict preservation is required. This execution did not run Syncthing-Fork, Android, a phone network or a public relay.
